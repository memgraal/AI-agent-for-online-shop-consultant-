# SSS AI Assistant

ИИ-сервис сайта магазина систем безопасности. Основа агента — LangGraph, HTTP API —
FastAPI. Каталог, CMS, 1С, CRM и постоянное хранилище документов пока не подключены;
соответствующие репозитории явно сообщают, когда источник данных недоступен.

## Структура

```text
app/
  agents/       customer.py, admin.py, общий цикл LangGraph и состояние
  api/          отдельные маршруты, схемы и проверка доступа администратора
  prompts/      отдельные системные промпты для клиента и администратора
  repositories/ контракты доступа к каталогу, документам, заказам и аналитике
  services/     общие сервисы, включая маскирование персональных данных
  tools/        раздельные инструменты, доступные соответствующему агенту
```

## Запуск

Нужен Python 3.11+.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e .
cp .env.example .env
```

Для разработки установите `pip install -e '.[test,lint]'`. Полный локальный набор
проверок обоих приложений:

```bash
python -m pytest -q tests
python -m pytest -q faq_workbench/tests
python -m ruff check app tests scripts
cd faq_workbench && python -m ruff check faq_workbench tests
```

Эти проверки также запускаются в GitHub Actions для Python 3.11 и 3.12.

Заполните `LLM_API_KEY`, настройте провайдера и задайте отдельный секрет
`ADMIN_API_KEY`, затем запустите:

```bash
uvicorn app.main:app --reload
```

`GET /health` проверяет, что процесс отвечает; `GET /ready` возвращает `503`, пока не
заданы настройки обеих моделей и административный ключ. Readiness проверяет наличие
конфигурации, но не делает платные пробные вызовы к провайдерам.

Swagger UI: <http://localhost:8000/docs>. Состояние сервиса: `GET /health`.

## Пользовательский чат

Для основного клиентского интерфейса используйте постоянное WebSocket-соединение
`/api/chat/ws` (в production — `wss://`). Клиент отправляет JSON-кадр с полями
`message`, `stream` (`false` по умолчанию), `detail`, необязательными `history`,
`conversation_id` и `request_id`:

```json
{
  "request_id": "turn-1",
  "message": "Подбери охранную систему для коттеджа 140 м²",
  "stream": false,
  "detail": "quick"
}
```

При `stream: false` сервер возвращает кадр `result` с готовым ответом и
`conversation_id`. При `stream: true` сервер присылает отдельные JSON-кадры типов
`progress`, `token`, затем `done`; ошибка передаётся кадром `error`. В каждом кадре
ответа возвращается `request_id`. Одно соединение закрепляется за одним диалогом:
после первого ответа следующие запросы могут не передавать `conversation_id`.
Запросы внутри соединения обрабатываются последовательно.

`POST /api/chat`

```json
{
  "message": "Подбери охранную систему для коттеджа 140 м²",
  "history": [],
  "detail": "quick"
}
```

Пользовательский агент может подбирать и сравнивать товары, искать сведения в
документах, помогать с реквизитами и корзиной, а также предлагать вызвать оператора.
Ему доступны только соответствующие клиентские инструменты.

Для интерфейса с печатью ответа по мере генерации используйте `POST /api/chat/stream`.
Он отправляет Server-Sent Events: `progress`, `token`, `done` или `error`.
HTTP-маршруты оставлены для совместимых интеграций: `POST /api/chat` возвращает
готовый ответ, а `POST /api/chat/stream` — SSE.

Для ручной проверки из терминала установи зависимости проекта командой
`pip install -e .`, запусти API, затем во втором терминале выполни
`python scripts/chat_ws.py`. Вводи вопросы после `Вы:`; `/new` начинает отдельную
сессию, `/exit` завершает клиент. Флаг `--stream` включает вывод ответа по мере
генерации, а `--detail detailed` переключает подробный режим.

Все варианты чата и административный endpoint принимают необязательный
`conversation_id`. Первый ответ возвращает ID; передавайте его в следующих запросах,
чтобы сервер подставлял историю сам. Пока сессии хранятся в памяти одного процесса
(до 24 часов бездействия), теряются при перезапуске и не подходят для нескольких
worker-процессов. Для постоянного хранения истории понадобится отдельное хранилище.

### Восстановление чата после обновления страницы

API уже продолжает существующую сессию, если клиент повторно отправляет её
`conversation_id`. Для сохранения чата в той же вкладке фронтенду нужно хранить в
`sessionStorage` ID сессии и список сообщений, отображаемых пользователю. При загрузке
страницы интерфейс восстанавливает список сообщений и открывает WebSocket заново; в
первом кадре после подключения передаёт сохранённый `conversation_id`. Для HTTP тот же
ID передаётся в каждом запросе. `sessionStorage` переживает обновление страницы, но
очищается при закрытии вкладки, что подходит для сессии «пока открыто окно».

Если сервер ответил `conversation_not_found` (например, после перезапуска процесса или
истечения 24 часов), клиент может начать новую серверную сессию без `conversation_id`
и передать сохранённые сообщения в `history`. Новый ответ вернёт новый ID. Кнопка
«Новый диалог» должна удалить сохранённые ID и сообщения. Пока на фронтенде это не
реализовано, API сам не может восстановить ID, который браузер потерял при обновлении.

Подготовлен экспериментальный контур RAG без БД: администратор может добавить текст
документа через `POST /api/admin/assistant/knowledge/documents` (заголовок
`X-Admin-Key`), а клиентский агент ищет совпадающие фрагменты через инструмент
`search_knowledge_base`. Тело содержит `document_id`, `title`, `text` и необязательные
`source_url`, `product_sku`, `section`, `page`. Список доступен через GET на тот же
путь. Файлы можно отправить через `POST /api/admin/assistant/knowledge/documents/upload`
как multipart-поле `file`; поддерживаются `.txt`, `.md`, `.pdf` и `.docx`. Размер
ограничен `KNOWLEDGE_MAX_UPLOAD_BYTES`, извлечённый текст — `KNOWLEDGE_MAX_TEXT_CHARS`,
а PDF ограничен `KNOWLEDGE_MAX_PDF_PAGES`; для DOCX также проверяется общий размер
распаковываемого содержимого.
Это индекс ключевых слов в памяти процесса, не векторный поиск; данные теряются при
перезапуске и не синхронизируются между worker-процессами. При пустом индексе поиск
возвращает пустой список, а не выдуманные сведения. Для URL, эмбеддингов, разграничения
прав и постоянного векторного хранилища нужен отдельный этап.

Если пользователь просит подготовить вводные для специалиста или монтажника,
ассистент может собрать предварительное ТЗ: перечислить данные объекта, показать
заполненность основных требований и отметить, что требуется уточнить. Это не инженерный
расчёт и не рекомендация конкретной модели.

Инструмент `create_installation_brief` уже формирует консультационный бриф по типу и
площади объекта, зонам, целям охраны, каналам связи, автономности и ограничениям.
Он помогает собрать требования, но не подменяет подбор из каталога или инженерный
проект.

## Ассистент админ-панели

`POST /api/admin/assistant/chat`, заголовок `X-Admin-Key: <ADMIN_API_KEY>`.

Тело запроса такое же, как у пользовательского чата. Админский агент помогает
подготавливать SEO-черновики, нормализовать импортированные атрибуты, искать возможные
дубли и анализировать частые вопросы. Его инструменты не доступны пользовательскому
агенту; действия описаны как черновики и не публикуются автоматически.

Инструмент SEO-карточки принимает название, производителя и характеристики. JEv
возвращает категорию, тип, назначение и теги товара; основная модель формирует описание,
H1, meta title/description и текст категории. Также возвращаются критерии похожих
товаров по производителю, типу и назначению. Результат остаётся черновиком и не меняет
каталог.

Для отдельной классификации товара используйте
`POST /api/admin/assistant/products/classify`. JEv возвращает только проверенный
Pydantic-объект с полями `category`, `product_type`, `purpose`, `tags`; эту структуру
можно сохранять или передавать следующему этапу обработки.

Для генерации с фиксированным JSON-контрактом используйте
`POST /api/admin/assistant/products/seo-draft`. В отличие от `/chat`, этот маршрут
возвращает поля напрямую по схеме `ProductContentDraft`, без дополнительного
переформатирования ответа чат-моделью:

```bash
curl -sS http://127.0.0.1:8000/api/admin/assistant/products/seo-draft \
  -H 'Content-Type: application/json' \
  -H "X-Admin-Key: $ADMIN_API_KEY" \
  -d '{
    "name": "Уличная IP-камера X-100",
    "manufacturer": "Русичи",
    "attributes": "Разрешение 4 Мп, корпус IP66"
  }'
```

Операции каталога принимают данные только из запроса и возвращают Pydantic-ответы:

- `POST /api/admin/assistant/catalog/normalize-attributes` предлагает нормализацию,
  сохраняя исходные значения и объяснение; каталог не меняется.
- `POST /api/admin/assistant/catalog/duplicate-candidates` находит вероятные пары
  среди переданных карточек (до 100 за запрос из-за попарной сложности алгоритма);
  решение о слиянии принимает человек.
- `GET/PUT /api/admin/assistant/content` управляет тоном, отключёнными темами и
  утверждёнными FAQ; `GET /api/admin/assistant/content/history` показывает историю
  настроек в текущем процессе.
- `GET /api/admin/assistant/operator-requests` показывает локальные заявки. Без CRM
  или подключённого оператора очередь не означает доставку обращения.

Без БД также доступны `POST /api/orders/validate-company-details` (формат и контрольные
суммы ИНН/ОГРН, но не существование компании) и `POST /api/orders/calculate-total`
(арифметика только по переданным ценам и правилам скидок). Это не источник истины
магазина. Базовый HTTP rate limit настраивается через `API_RATE_LIMIT_MAX_REQUESTS`,
`API_RATE_LIMIT_WINDOW_SECONDS` и `API_RATE_LIMIT_MAX_CLIENTS`; для нескольких worker
его нужно дополнить ограничением на прокси. Число одновременных обращений к моделям и
максимальное ожидание в очереди задаются `LLM_MAX_CONCURRENT_REQUESTS` и
`LLM_QUEUE_TIMEOUT_SECONDS`. Диалоги ограничены `CHAT_MAX_SESSIONS`; запросы к одному
диалогу выполняются последовательно, чтобы параллельные ответы не теряли историю.
Потоковая выдача передаёт фрагменты провайдера без искусственной задержки по символам.

Для отдельной подготовки FAQ-кандидатов добавлено приложение
[FAQ Workbench](./faq_workbench/README.md). Он принимает вопросы после отправки в чате,
считает повторы, записывает обращения в собственную PostgreSQL и при пакетном обновлении
вызывает основной сервис по защищённому API. После проверки администратором кандидаты
публикуются через API в поле часто задаваемых вопросов. У FAQ API собственные настройки,
зависимости и переменные окружения; HTML интерфейса там нет. Пока FAQ API не связан с
агентом, фронтенд отправляет вопрос отдельно в оба API. Публичный API Workbench также
ограничивает частоту запросов на процессном уровне; нескольким workers нужен общий
лимитер reverse proxy.

## Ограничение вызовов по домену

Задайте `ALLOWED_ORIGINS` точными origin фронтенда через запятую, например
`https://shop.example.ru`. Настройка действует на HTTP API, а WebSocket чата проверяет
этот же origin отдельно. Это ограничение браузерных источников, не замена
аутентификации: backend-клиент может подделать `Origin`, поэтому для публичного API
нужны rate limit/WAF на reverse proxy. Административные операции защищаются ключом.

## Текущее состояние и безопасность

- История передаётся клиентом в каждом запросе, сервер её не сохраняет.
- Перед отправкой модели сообщения пользователя маскируют типовые email, телефон и
  длинные числовые идентификаторы. Это базовая фильтрация, не полноценная DLP.
- Каталог, цены, наличие, скидки магазина и аналитика не подключены; агент не должен
  выдавать вымышленные данные. API предварительного расчёта по переданным ценам и
  локальная очередь обращений не являются интеграцией с заказами или CRM.
- База знаний, очередь обращений, настройки контента и rate limit хранят состояние
  только в памяти процесса; при рестарте оно сбрасывается.
- Переменные окружения перечислены в `.env.example`.

### Масштабирование процесса

Основной AI-сервис сейчас использует ограниченные, но процессные хранилища для диалогов,
базы знаний, настроек контента, очереди оператора и rate limit. Данные сбрасываются при
рестарте и не разделяются между workers; до переноса этих хранилищ в общий Redis или
PostgreSQL запускайте один worker. FAQ Workbench уже хранит бизнес-данные в PostgreSQL,
но его локальный rate limit также нужно вынести на общий reverse proxy при нескольких
workers. Лимит параллельных запросов к LLM задаётся на каждый процесс.

## Провайдеры моделей

Модель и провайдер настраиваются в `.env`:

- `LLM_PROVIDER=openai`: официальный OpenAI API, `LLM_MODEL` — имя модели.
- `LLM_PROVIDER=yandex`: Yandex Cloud AI Studio. Используйте API-ключ сервисного
  аккаунта со scope `yc.ai.languageModels.execute`, например
  `LLM_MODEL=gpt://<folder_id>/yandexgpt/latest`.
  По умолчанию используется `https://ai.api.cloud.yandex.net/v1`.
- JEv использует TypeSafe SDK отдельно от модели чата. Укажите ключ RouterAI в
  `JEV_LLM_API_KEY`; по умолчанию используются `JEV_LLM_MODEL=typesafe/jev-1.14`
  и `JEV_LLM_BASE_URL=https://routerai.ru/api`.
- `LLM_PROVIDER=openai-compatible`: любой совместимый с Chat Completions endpoint,
  например локальный Ollama или ваш шлюз. Укажите `LLM_BASE_URL` и имя модели;
  API-ключ может быть пустым для локального сервера.

`LLM_*` задают основную модель чата, а `JEV_LLM_*` — отдельный JEv-классификатор.
В FAQ-анализе JEv назначает категорию каждому вопросу, а основная модель группирует
вопросы внутри категорий и формирует текстовые поля. В админском SEO-инструменте JEv
выбирает категорию, тип и назначение товара из контролируемых вариантов и оценивает
исходные фрагменты как теги; основная модель готовит описание,
H1, метатеги и текст категории. Текстовая модель не переопределяет классификацию.
Смена JEv не меняет модель чата. Конкретные возможности tool calling и streaming
зависят от выбранной модели. Интеграции с API Anthropic и Google Gemini требуют
отдельных адаптеров.

Пример для Yandex AI Studio:

```dotenv
LLM_PROVIDER=yandex
LLM_API_KEY=ваш_секретный_ключ
LLM_MODEL=gpt://ваш_folder_id/yandexgpt/latest
LLM_BASE_URL=https://ai.api.cloud.yandex.net/v1
```

Сравнение провайдеров, технические риски текущей версии и план проверки перед запуском
описаны в [техническом и рыночном обзоре](docs/TECHNICAL_AND_MARKET_REVIEW.md).

## Логирование

Приложение пишет события в stdout и в ротируемый файл `logs/sss-ai.log`.
Формат по умолчанию — JSON Lines: одна JSON-запись на строку. Файл ротируется при
достижении `LOG_MAX_BYTES`, хранится до `LOG_BACKUP_COUNT` архивных файлов.

Основные настройки:

- `LOG_LEVEL` — `DEBUG`, `INFO`, `WARNING`, `ERROR` или `CRITICAL`.
- `LOG_FORMAT` — `json` или удобный для чтения `text`.
- `LOG_FILE` — путь к журналу; пустое значение выключает запись в файл, оставляя stdout.
- `LOG_MAX_BYTES` и `LOG_BACKUP_COUNT` — размер файла и число архивов.
- `LLM_TIMEOUT_SECONDS` — таймаут запроса к выбранному провайдеру.
- `LLM_QUICK_MAX_OUTPUT_TOKENS` / `LLM_MAX_OUTPUT_TOKENS` — предел генерации для
  быстрого и подробного режима.
- `CHAT_CONTEXT_MAX_MESSAGES` — сколько последних сообщений истории передавать модели
  на каждом ходе (по умолчанию 20, то есть около 10 пар вопрос–ответ). Сессия хранит
  до 40 сообщений, чтобы не терять предыдущий контекст между ходами.
- `CHAT_MAX_CONTEXT_TOKENS` — примерный общий бюджет токенов сообщений диалога на один
  ход. Старые сообщения отбрасываются первыми; слишком длинный текущий вопрос получает
  `413`. Оценка использует `tiktoken` и может отличаться от подсчёта провайдера;
  системный промпт и описания инструментов в этот бюджет не входят.
- `AGENT_MAX_LLM_CALLS` — максимальное число обращений к модели за один ход (по умолчанию
  6), включая
  вызовы после инструментов. Ограничивает повторные генерации вместе с лимитом токенов
  на один ответ.
- `AGENT_RECURSION_LIMIT` — максимальное число графовых шагов за один запрос.

В событиях доступны request ID, метод и путь, HTTP-статус, длительность запроса,
тип агента, имя инструмента/репозитория, количество сообщений и токены модели, если
провайдер вернул статистику использования. Содержимое сообщений, ответы, аргументы
инструментов, ключи авторизации и заголовки запроса в логи не записываются.
Для ошибки сохраняется тип исключения, но не текст внешней ошибки, который может
содержать переданные данные.
