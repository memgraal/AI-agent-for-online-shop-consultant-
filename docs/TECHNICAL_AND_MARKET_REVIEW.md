# Технический и рыночный обзор SSS AI Assistant

Дата обзора: 13 октября 2026 года. Срез по возможностям провайдеров сделан по
официальной документации; перед коммерческим выбором нужно отдельно проверить договор,
обработку данных, доступность моделей в аккаунте, стоимость и фактическое качество на
репрезентативном наборе вопросов магазина.

## Краткий вывод

Для первой российской версии разумный кандидат — Yandex Cloud AI Studio с YandexGPT Pro
как основным агентным профилем и более лёгкой моделью для быстрых, узких задач. Это
позволяет использовать русскоязычный продуктовый стек и OpenAI-совместимый интерфейс,
не привязывая LangGraph к одному провайдеру. OpenAI-совместимый адаптер также оставляет
путь к локальным моделям. Выбор не следует закреплять без сравнительного теста на
реальных вопросах по безопасности и каталогу.

## Поддержка провайдеров в коде

Провайдер создаётся в `app/providers/chat_model.py`; имена, ключи и endpoint’ы задаются
переменными окружения. Сейчас предусмотрены:

| Провайдер | Интеграция | Для чего подходит | Ограничение |
| --- | --- | --- | --- |
| OpenAI | Chat Completions через `ChatOpenAI` | Контрольный внешний кандидат для качества диалогов и функций | Передавать клиентские данные можно только после оценки требований к хранению и договору |
| Yandex AI Studio | OpenAI-совместимый API, ключ Yandex Cloud, URI модели вида `gpt://<folder>/yandexgpt/latest` | Русскоязычный клиентский сервис; возможный основной провайдер для проекта | Нужно проверить доступные именно в аккаунте модели и контракты function calling/streaming |
| OpenAI-compatible | Настраиваемый `LLM_BASE_URL`, модель, необязательный ключ | Локальные или альтернативные сервисы, включая Ollama и OpenAI-совместимые шлюзы | «Совместимость» не означает одинаковое качество tool calling: проверять каждую модель отдельно |

Anthropic Claude и Google Gemini рассмотрены как внешние рыночные альтернативы, но в
коде не объявлены рабочими провайдерами. Их API и обработка tools отличаются, поэтому
для них нужны отдельные LangChain адаптеры и тестовый контракт, а не только замена URL.

## Качественный обзор рынка

| Семейство | Сильная сторона для проекта | Что проверить до выбора |
| --- | --- | --- |
| YandexGPT в AI Studio | Русский язык и OpenAI-совместимый API; удобно поставить рядом с текущим графом | Точность извлечения параметров, tool calling на заданных схемах, latency, цена, договор и условия обработки данных |
| OpenAI | Широкая API-экосистема и зрелые инструменты интеграции | Доступность, данные и коммерческие ограничения в целевой среде, стоимость длинных диалогов |
| Gemini | Сильная мультимодальность и большие контекстные окна у отдельных моделей; полезно для разбора инструкций с изображениями | Доступность, региональные требования, качество русского технического текста, отдельная интеграция и извлечение цитат |
| Claude | Сильный tool-use/агентный сценарий в Messages API; полезен как сравнительный кандидат на многошаговые диалоги | Это не OpenAI Chat Completions API: отдельный адаптер, доступность для целевого рынка и цена |
| Локальные модели через Ollama/совместимый endpoint | Максимум контроля над размещением данных и возможность эксперимента без внешнего inference API | Стоимость GPU/дежурства, скорость, стабильность, безопасность модели, поддержка корректных tool calls и обновлений |

Официальные документы подтверждают OpenAI-совместимость Yandex Foundation Models,
адрес AI Studio `https://ai.api.cloud.yandex.net/v1`, формат URI модели `gpt://...` и
использование ключа Yandex Cloud со scope `yc.ai.languageModels.execute`; документация провайдера также указывает на приоритет
русского языка у YandexGPT. [Yandex Cloud: совместимый API и подключение к моделям](https://yandex.cloud/en/docs/tutorials/ml-ai/ai-model-ide-integration),
[Yandex Cloud: создание агента и scope ключа](https://yandex.cloud/en/docs/tutorials/serverless/create-ai-agent-function),
[Yandex Cloud: API-ключи и scope](https://yandex.cloud/ru/docs/iam/concepts/authorization/api-key),
[Yandex Cloud: модели и язык](https://yandex.cloud/en/docs/foundation-models/concepts/yandexart/).

Сравнение не оценивает качество по рекламным рейтингам. Для этого проекта критичнее
правильность вызова инструментов, отказ от неподтверждённых характеристик, русский язык,
извлечение данных из паспорта оборудования, задержка и совокупная цена. Gemini описывает
function calling и мультимодальные/длинноконтекстные режимы в собственной документации;
Anthropic описывает отдельный протокол tool use; Ollama документирует OpenAI-совместимые
endpoint’ы и поддержку инструментов у отдельных моделей. [Gemini: function calling](https://ai.google.dev/gemini-api/docs/function-calling),
[Gemini: модели и контекст](https://ai.google.dev/gemini-api/docs/models),
[Anthropic: tool use](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview),
[Ollama: tool support](https://ollama.com/blog/tool-support).

## Технический аудит текущего проекта

### Что уже есть

- Клиентский и административный маршруты разделены; для админского API проверяется
  отдельный ключ.
- Граф использует async-вызовы и ограничение глубины; инструменты и репозитории имеют
  асинхронные интерфейсы.
- Тексты обычных чатов не записываются в логи; пользовательский ввод маскирует несколько
  распространённых форматов контактов и длинных чисел.
- Provider factory отделяет бизнес-граф от транспорта и держит параметры моделей в env.
- Добавлен SSE endpoint для пользовательского streaming-ответа и предварительное ТЗ
  монтажнику с полнотой вводных и вопросами, которые остаётся уточнить.

### Что блокирует полноценный продуктовый подбор

- Репозитории каталога, заказов, документов и аналитики пока являются заглушками.
  Значит, реальные подбор, цены, остатки, совместимость, скидки и ссылки на документы
  ещё не работают. Агент должен оставаться честным об отсутствии данных.
- История диалогов хранится в памяти одного процесса, пропадает при перезапуске и
  не синхронизируется между worker-процессами. Для production нужны долговременное
  хранилище, восстановление после сбоев и проверка прав доступа к сессиям.
- Админский доступ пока защищён одним статическим API-ключом. Для production нужны
  пользовательская идентификация, роли, ротация ключей, аудит операций и rate limiting.
- Маскирование PII основано на регулярных выражениях и не является DLP. Нельзя считать,
  что оно выявит адреса, номера договоров, свободно описанные персональные данные и все
  форматы документов.
- Внешняя модель может по-разному поддерживать схему инструментов, streaming и JSON.
  Требуется матрица совместимости по конкретным версиям моделей, а не только по бренду.
- Сейчас нет лимита расходов по пользователю, метрик реальной latency, health-check
  провайдера и стратегии fallback. Повторные запросы к другой модели следует включать
  только с явным бюджетом и проверкой, что повтор не продублирует бизнес-операцию.

### Обязательные проверки перед production

1. Проверить точность маршрутизации и tool calls на наборе русскоязычных вопросов по
   Livi, Stemax, RiDom, Teko, Октава и другим брендам из ТЗ; пока каталог не подключён,
   использовать подготовленный тестовый корпус, не выдавая его за реальный магазин.
2. Для каждого провайдера проверить: обычные ответы, нулевой вызов инструмента,
   один/несколько вызовов, ошибки/timeout, длинный ответ, потоковые chunks и отмену
   клиентского запроса.
3. Измерять p50/p95 времени ответа, точность атрибутов, долю отказов и стоимость с учётом
   всех циклов tool calling. Не сравнивать только цену одного completion.
4. Проверить промпт-инъекции в загруженных инструкциях, отказ на небезопасную
   электромонтажную консультацию, утечки PII и обход админского доступа.
5. Подключить retrieval с метаданными производителя, артикула, версии документа и
   страницы; возвращать ссылку и цитируемый фрагмент из найденного источника.

## Функции, добавленные для клиентского опыта

1. **Ответ токенами и статусом работы.** `POST /api/chat/stream` отправляет события
   `progress`, `token`, `done` или нейтральную ошибку, чтобы чат ощущался отзывчивым и
   показывал безопасный прогресс проверки каталога/документов.
2. **Предварительное ТЗ на объект.** По просьбе клиента формируется структурированный
   JSON-бриф для передачи менеджеру или монтажнику. Он отмечает заполненность базовых
   требований и вопросы для уточнения. Бриф не является готовой схемой, сметой или
   подтверждённым подбором оборудования.

Эти функции работают без БД и не маскируют отсутствие реальных данных каталога.
