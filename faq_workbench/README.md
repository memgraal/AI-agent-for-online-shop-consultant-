# SSS FAQ API

Самостоятельный API-сервис для накопления пользовательских вопросов и подготовки
часто задаваемых вопросов. У него собственные зависимости, настройки и PostgreSQL.
Он не импортирует код основного AI-приложения: для семантической группировки вызывает
только его HTTP endpoint. HTML-фронтенда в этом приложении нет.

## Запуск

Нужен Python 3.11+ и PostgreSQL. В корне репозитория:

```bash
cd faq_workbench
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Задайте переменные окружения (значения секретов храните в secret manager):

```dotenv
FAQ_DATABASE_URL=postgresql+asyncpg://faq_user:secret@127.0.0.1:5432/sss_faq
FAQ_ADMIN_API_KEY=long-random-secret-for-faq-admin
FAQ_AI_SERVICE_URL=http://127.0.0.1:8000
FAQ_AI_ADMIN_API_KEY=тот-же-секрет-что-ADMIN_API_KEY-основного-сервиса
FAQ_ALLOWED_ORIGINS=https://shop.example.ru
FAQ_AI_API_TIMEOUT_SECONDS=90
FAQ_API_RATE_LIMIT_MAX_REQUESTS=120
FAQ_API_RATE_LIMIT_WINDOW_SECONDS=60
FAQ_API_RATE_LIMIT_MAX_CLIENTS=10000
FAQ_ANALYSIS_MIN_NEW_QUESTIONS=50
FAQ_ANALYSIS_MIN_INTERVAL_HOURS=24
FAQ_EMBEDDING_SIMILARITY_THRESHOLD=0.82
```

```bash
alembic upgrade head
uvicorn faq_workbench.main:app --host 0.0.0.0 --port 8010
```

Для запуска тестов установите `pip install -r requirements-dev.txt`, затем выполните
`pytest` из каталога `faq_workbench`.

Сервис доступен по `http://localhost:8010`, OpenAPI — `/docs`, проверка состояния
PostgreSQL — `GET /health`. Схема PostgreSQL версионируется миграциями Alembic.
Для новой базы выполните `alembic upgrade head`. Если таблицы уже созданы предыдущей
версией через `create_all`, сначала сверьте их со схемой первого revision, затем
выполните `alembic stamp 20261023_01 && alembic upgrade head`.

## Поток данных

Фронтенд после отправки сообщения в чат делает отдельный запрос на FAQ API:

```http
POST /api/questions
Content-Type: application/json
Origin: https://shop.example.ru
```

```json
{
  "event_id": "a7a14b70-a9a4-43c8-a9d4-a883367ae43e",
  "conversation_id": "chat-session-id",
  "question": "Работает ли сигнализация без интернета?"
}
```

`event_id` создаёт фронтенд для конкретной отправки и повторно использует его при
сетевом retry: это делает учёт обращения идемпотентным. В базе сохраняются вопрос,
его нормализованное представление, частота, время и ID диалога. Типовые email и
телефоны маскируются перед записью. Вопросы с одинаковым нормализованным текстом
считаются одним пунктом. Запрос только записывается в PostgreSQL и обновляет частоту;
ни эмбеддинг, ни генеративная модель на отправке сообщения не вызываются.

Пересчёт удобно вызывать планировщиком раз в час:

```http
POST /api/admin/faq/rebuild?limit=100
X-FAQ-Admin-Key: <FAQ_ADMIN_API_KEY>
```

Первичный пересчёт ждёт порога в 50 новых уникальных формулировок; для начальной
проверки малого набора используйте `?force=true`. После первого успешного запуска
пересчёт пропускается, пока не появится 50 новых формулировок; если поступали новые,
но порог не набрался, пересчёт всё равно запускается раз в 24 часа. Повторы известных формулировок сразу
обновляют частоту опубликованных FAQ в PostgreSQL и не расходуют токены. Для ручного
запуска без порога используйте `?force=true`.

Во время пакетного пересчёта локальная multilingual embedding-модель вычисляет
векторы для новых формулировок и кеширует их в PostgreSQL. Семантически близкие вопросы
схлопываются по cosine similarity; частота суммируется. Далее не более 100 групп с
объединёнными частотами и до пяти примеров вариантов на группу передаются защищённому
`POST /api/admin/faq/analyze` основной AI-системы для проверки смысловых групп и
формирования общей формулировки. Это batch-вызов, а не вызов модели на каждый вопрос.
Кандидаты остаются черновиками, их источники доступны администратору через
`GET /api/admin/faq/candidates`; одобренный пункт публикуется через
`POST /api/admin/faq/candidates/{id}/publish`. Фронтенд получает только опубликованные
вопросы через `GET /api/faq`. Агрегированные формулировки и общее число событий
доступны через `GET /api/admin/faq/questions`; снять пункт с публикации можно через
`DELETE /api/admin/faq/candidates/{id}`. Ответы FAQ и автоматическая публикация не
создаются.

Эмбеддинги строятся локально библиотекой FastEmbed и не используют LLM-токены. Первая
пакетная обработка скачивает multilingual MiniLM модель (около 0.22 GB); она
поддерживает русскоязычные тексты. Значение сходства по умолчанию настраивается через
`FAQ_EMBEDDING_SIMILARITY_THRESHOLD`. Его следует откалибровать на размеченных парах
вопросов магазина до массовой публикации: слишком низкий порог склеивает разные темы,
слишком высокий оставляет больше перефразировок отдельно.

Пока агент не подключён к базе данных и не вызывает `/api/questions` автоматически.
До этого момента интеграция на фронтенде может отправлять тот же вопрос параллельно
в чат и в FAQ API.

## CORS и доступ

`FAQ_ALLOWED_ORIGINS` задаёт список разрешённых точных origin через запятую, например
`https://shop.example.ru,https://admin.example.ru`. Не указывайте путь или завершающий
слэш. Для браузерных запросов сервис отклоняет другой `Origin`; WebSocket API агента
тоже проверяет origin. Основному сервису задайте `ALLOWED_ORIGINS` с тем же списком.

CORS/origin ограничение помогает контролировать вызовы из браузеров, но не является
аутентификацией: внешний скрипт или сервер может подделать заголовок `Origin`. Поэтому
публичный чат дополнительно ограничивайте rate limit/WAF на reverse proxy, а секреты
администратора используйте только на серверной стороне. `FAQ_ADMIN_API_KEY` и
`FAQ_AI_ADMIN_API_KEY` — разные границы доступа; второй совпадает с
`ADMIN_API_KEY` основной AI-системы и хранится только в окружении FAQ backend. Локальный
rate limit FAQ API конфигурируется переменными выше, хранится в памяти каждого worker
и не заменяет общий лимитер reverse proxy.

Сервис пишет структурированные JSON-события в stdout. Логируются ID запроса, HTTP
метаданные, длительность и счётчики; тексты вопросов и заголовки с секретами в журнал
не попадают. Уровень задаётся через `FAQ_LOG_LEVEL`.
